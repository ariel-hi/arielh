## Requirements and local preview

Use Node.js and Python 3.9+ for the build, checks, and release tooling. The root project has no npm package dependencies. PHP 8.1+ with PDO SQLite and writable private directories is required for the score API and statistics.

For a static preview:

```sh
python -m http.server 8080 --bind 127.0.0.1
```

Open `http://127.0.0.1:8080/`. To exercise the PHP leaderboards locally, use a configured PHP runtime instead:

```sh
php -S 127.0.0.1:8080 -t .
```

These development servers do not enforce Apache `.htaccess` rules. Keep them bound to localhost; private-directory protection must be verified on the deployed Apache host. Analytics deliberately excludes local visits.

## Leaderboards and statistics

The leaderboard API stores only submitted nicknames and scores in `.leaderboards-private/scores.sqlite`. Grid16 scores use integer tenths of a second; Shooter uses whole points. Each game keeps its top 1,000 scores. The API limits accepted submissions globally to 120 per minute and does not store visitor IPs, cookies, or user identifiers. Scores are reported by the browser rather than independently verified by the server.

Statistics are enabled on the current deployment. A fresh installation stays disabled until `.analytics-private/config.php` contains a valid owner password hash and `enabled` is set to `true`. On a new server, copy `.analytics-private/config.example.php` to `config.php`, set a hash generated with PHP's `password_hash()`, and enable collection only after PHP/PDO SQLite, private-directory HTTP denial, and storage permissions have been verified. Store the hash, never the plaintext password, in this configuration. The current owner's access details are in the ignored local `.verification/analytics-owner-access.txt`; this file must never be uploaded.

When enabled, statistics keep daily aggregate counts for pageviews, project opens, filter changes, and game starts, plus referrer domains and broad screen groups. They exclude URL queries, full referrer URLs, visitor identities, IPs, and measurement cookies, and respect Do Not Track and Global Privacy Control. Totals older than 180 days are deleted when a visit is counted or Stats is opened. `/analytics/dashboard.php` requires the owner password and uses a secure session cookie for dashboard authentication only; an unconfigured dashboard returns HTTP 503. Login attempts are reserved under a global file lock before password verification, so simultaneous sessions share the same 12-attempt limit.

Private configuration, databases, and session files are ignored by Git and excluded from releases. Both private directories include Apache denial rules; verify that the deployed host honors them. Existing server-side configuration and data must be preserved during updates.

The deployed owner dashboard recorded five pageviews, one project open, one filter change, and one Gems game start during verification with normal Chrome visits. Private configuration and analytics storage use the host's 0604 permissions behind verified HTTP 403 responses; the leaderboard database is 0600 and the dashboard session directory is 0700. The complete root and nested-file permission record is kept locally in `.verification/live-file-permissions.json`.

## Package and deploy

After verification passes:

```sh
npm run package
python scripts/deploy-sftp.py
```

Packaging runs the build and site check, then produces `.release/site/`, `.release/site-manifest.json`, and `.release/arielh-release.zip`. The explicit upload list excludes development pages, source maps, original photos, tooling, credentials, and private runtime state. The manifest records each file's size and SHA-256 hash. Every ZIP entry explicitly uses Unix regular-file mode 0644 so Windows-created archives do not extract as world-writable files.

For an incremental Explorer update, first preserve the last verified live manifest as a baseline, such as `.release/live-manifest.json`. After building and checking the next release, package only its changed files:

```sh
python scripts/package-update.py --baseline .release/live-manifest.json --tag next-update --split-phases
```

The helper verifies staged hashes, refuses file removals, and writes `.release/.arielh-update-next-update.zip` with Unix 0644 metadata. It also records an unapplied update in `.verification/pending-release-next-update.json`. Choose a fresh tag for each update; reusing a tag replaces its local archives and pending record. Creating an archive does not publish it. Use the last verified live manifest as the baseline, never an unshipped build.

For Explorer uploads, `--split-phases` also creates separate `-assets.zip` and `-html.zip` archives when that phase has changed files. Upload and extract the assets archive first, then verify each asset's live SHA-256 against the phase's file records in the pending JSON. Only after those bytes match should you upload and extract the HTML archive. Use these phase archives instead of the combined ZIP for this workflow. Finish with the complete HTTPS verification before recording the update as applied.

Nested HTML entries are listed before parent pages, but Explorer may choose a different overwrite order. If a parent page requires new markup from an iframe page, publish and verify that child page separately before the parent. The phase records include each archive's size, hash, and exact file list; empty phases are omitted. The default command without `--split-phases` keeps its existing single-archive behavior.

The deployment command defaults to a local dry run. It validates the staged files without contacting the host, even when hosting configuration is missing. A successful dry run does not confirm remote access or publish anything.

The SFTP helper is an optional deployment route; the current IONOS account has no SFTP user configured. To use it later, copy `scripts/deploy.example.json` to the ignored `deploy.local.json` and set the real SFTP host, username, port, and webroot. Supply authentication through `keyFile` or the environment variable named by `passwordEnv`. Configure a trusted `knownHosts` file or an independently verified `hostKeySha256` fingerprint; unknown host keys are never accepted silently. A `/` webroot requires `allowRootWebroot: true` and an account restricted to this website.

Before the first upload, inspect the existing webroot `.htaccess`. Preserve any hosting PHP handler or unrelated routing directives in the local `.htaccess`, then rebuild the package. The deployment helper replaces this file with the packaged version; its backup preserves the original but does not merge server-specific settings automatically.

Applying an upload also requires Paramiko:

```sh
python -m pip install paramiko
python scripts/deploy-sftp.py --apply
```

The helper checks local hashes and remote paths, downloads all replaced originals into `.release/backups/` before writing, and stages individual files before atomic rename. Assets and PHP upload before HTML. It does not delete site files, overwrite live private configuration/databases, or use a remove-and-replace fallback when atomic replacement is unavailable.

After upload, it verifies public HTTPS with normal certificate validation: asset hashes, actual denial of the uploaded private configuration template, private database URLs, PHP route behavior, and uncached JSON from both leaderboard APIs. It reports dashboard readiness separately; HTTP 503 means configuration or server storage still needs attention. A transfer or verification failure is reported with the local backup location; no automatic rollback is attempted.

## SEO and search engines

`npm run build` regenerates titles, Open Graph/Twitter cards, JSON-LD structured data (Person, WebSite, VideoGame, CreativeWork, breadcrumbs) and `sitemap.xml` from `scripts/seo.js`. Standalone pages keep their markup; only the block between `<!-- seo:start -->` and `<!-- seo:end -->` is rewritten.

After a deploy, `npm run indexnow` notifies Bing, Yandex, Seznam and Naver. Google Search Console uses a DNS TXT record on the domain (no file or meta tag needed); submit `https://arielh.com/sitemap.xml` there and in Bing Webmaster Tools.

Analytics is first-party and cookieless (see `privacy.html`), so no consent banner is needed.
